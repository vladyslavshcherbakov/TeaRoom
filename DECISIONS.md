# Decisions

## Plan

The plan is in `docs/roadmap.md`. Its version in progress collects what is built until the user closes it. So a built step moves there from its planned version, and it is not removed, because the user wants to see what each version built. A rejected step is removed.

## Decisions

### Project

**TypeScript for a mobile Safari game.** The target is the mobile browser. Rejected: a native iOS app, because it would not run in the browser. Rejected: Phaser, which carried the 2D table in 0.2 and was removed when the game became a walkable 3D room.

**The room is real 3D in Three.js, seen from above at an angle, and controlled by taps.** A 3D room lets the camera change later, to first person or over the shoulder, by changing only the camera module and the tap rules. Seen from above, the whole small room fits a portrait phone, and one thumb is enough: a tap on the floor walks there, a tap on furniture walks to it and shows it close up. Rejected: isometric 2D sprites, because another camera would mean redrawing every picture. Rejected: first person as the start, because it needs looking around with a second gesture and a model of the hands.

**Three.js, Vite and TypeScript are pinned to exact versions, and CI installs from the lockfile.** A game's feel depends on the renderer's timing and input handling, and TypeScript's printer writes the code of the Claude artifact, so an update is a deliberate change with its own commit, not a side effect of a fresh install.

**No debug page next to the game.** The ritual bench drove the simulation with plain buttons and showed the log on a page. Nobody used it: the rules are checked by integration tests, the room by playing it, and the history by the log with its world report. It only had to be fixed after each change to the simulation. The log is read in the browser's console.

**The code becomes a reusable engine and a tea game on top of it.** The user wants to build other games on the same engine, such as a shooter, chess, a platformer or a tower defense, so nothing in the engine may know about tea. A second reason is that rules which live in the engine's structure cannot be forgotten: a command without its checks does not compile, while a convention in CONTRIBUTING.md is forgotten one handler at a time. The engine is made only of what the tea game already uses, and it is generalised further when a second game needs it. The steps are in `docs/roadmap.md`, after the review's fixes. Rejected: a general engine designed up front for every genre, because code that no game calls cannot be checked by playing. Rejected: a separate npm package now, because a folder with an import rule and a test of it keeps the line until a second game exists.

**No haptics on iPhone.** iOS Safari does not implement the Vibration API, and the checkbox-switch workaround is reported to stop working from iOS 26.5. Haptics stay a progressive enhancement for browsers that have the API.

### Shared/Simulation/

**A sip is too hot only above 93 °C.** A bowl from a boiling kettle stays above it for about five seconds after the pour, so a player who hurries can catch it and one who pauses misses it. At 70 °C, the first threshold, every bowl of the teas brewed near boiling made the player wait about half a minute before a good sip, and nothing told them to wait. Rejected: a tea bowl that cools faster, because tea would then turn lukewarm in about a minute.

**The simulation is a functional core with an imperative shell.** Commands and time go in, a new state and events come out, and nothing in `Shared/Simulation` knows about Three.js, the DOM or the clock. This keeps every rule testable without a browser, and lets AI-assisted changes to the presentation leave the rules alone. Rejected: game objects that hold their own state inside the renderer, because rules then live in meshes and cannot be tested headless.

**Player decisions are commands, consequences are events.** One command per decision, one event per thing the presentation or the world memory must react to. This gives replays, logs for debugging, and the ritual history the world memory will be built from. Rejected: an event bus where objects call each other, because one action has many consequences and the order would be decided by subscription order.

**Fixed simulation step of 0.05 s.** Cooling and brewing are not linear in time, so integrating once per frame gives different results at 30 and 60 frames per second. Twenty steps a second is well below what a phone can compute and fine enough for the curves. Rejected: variable steps, because the same ritual would taste different on a slower phone.

**Cooling is applied before heating in a step.** Heating caps at boiling, so cooling after it would keep a working kettle forever just below 100 °C.

**The simulation logs every decision, and the presentation decides where the lines go.** Events say what happened. The log says why: the temperature a judgement was made at, the value a refusal was decided on, what a pour left behind. Handlers collect lines in the draft, so the core stays free of side effects, and `RitualSession` writes them to an injected `RitualLog`. Each line carries the simulated time to the millisecond, and the sink adds the wall-clock time. Rejected: logging from the presentation by reading events, because the presentation never sees the values that decided the outcome.

**The world reports what changes every 5 s of simulated time, with rates over the next second.** Events and decisions alone left the history of a ritual without its numbers: how fast a bowl cooled with its lid open or closed, how the strength grew, how the cloth dried. The rates come from stepping a copy of the world one second ahead, so they are exactly what the rules will do, and no rule has to report itself. The lines are detail lines, since they come often. Only what is changing is reported, and a still room says so in one line.

**Broken content is caught before a room opens: loudly in development, quietly for players.** A definition that names a missing heater, vessel, figurine or tea is a developer's mistake no player can fix. `RitualSession.open` checks the whole catalog first. A development build throws with every problem listed, so the mistake cannot be missed. A player's build logs each problem at error level and returns `unavailable`, and the presentation shows a quiet screen instead of crashing mid-ritual. Rejected: throwing from `definitionIn` in a player's build, because the game would stop at the first lookup with nothing on screen.

**A refused command is an event, not an exception.** A player trying to pour from a closed thermos is part of play, and the presentation answers it materially: the item stays where it was, or the keeper answers in one line. Rejected: throwing, because a gesture would need a try block and a missed catch would stop the game.

**The ritual has no gods yet.** The game is only brewing tea for now. The gods' mood, remarks and plaque are a future feature in `docs/game-design.md` and the roadmap, and their rules are designed together with the plaque that shows them. Rejected: keeping a mood that nothing on screen shows, because its rules could not be judged by playing.

**Boiling water boils away, and only on a working heater.** A kettle forgotten on the heater loses its water, so leaving it there has a visible cost that grows with time: half a minute of boiling takes three fifths of a full kettle. A full kettle of cold tap water boils dry within a minute and forty-five seconds of switching the heater on, so the achievement for waiting until it boils dry does not ask a player to wait long. `Tests/Content/BoilingDry.integration.test.ts` holds that limit. The rate belongs to the heater, as the heat does. A vessel leaves the heater only by being picked up, so there is one way off the plate.

**Taking an item closes its lid.** A lid is not an item of its own, so it cannot stay behind, and leaving it open while carried would float it in the air. Closing it changes the rules visibly: a closed kettle keeps its heat, and a closed thermos cannot pour until its lid is tapped open again, which works on a held item too. An open lid lies on the surface beside its item. On a held item or one in the sink it stands open on its hinge, swung a little past upright, because a lid ajar over the opening stood in the tap's stream and the stream went through it. Lifting the kettle out of the sink counts as taking it, so its lid closes too.

**The kettle's water comes from the tap at the counter, and the kettle starts empty.** Filling the kettle is the first step of a ritual. The kettle stands in the sink under the tap, and the tap runs until the keeper turns it off, also while the keeper is away. Holding it under the tap tied the keeper to the counter, and the kettle walked away with them. Water that overflows runs down the drain and does not wet the table, because the table is where the ritual's spills count. Rejected: filling a kettle held in a hand as well, because two ways to do one thing made the tap's taps ambiguous.

**A continued visit lives through the time away, up to twelve hours, in steps of 1 s.** The world should not wait for the player: tea left in a bowl is cold when they come back, and a kettle left on the heater has boiled dry. Twelve hours settle everything, even the thermos, which takes hours to cool. Steps of 1 s are fine enough for the curves, and the whole absence works on one copy of the state, so twelve hours take about 70 ms. Rejected: freezing the world while away, because the room would not feel lived in, and the 0.05 s step for the absence, because twelve hours would take seconds on a phone.

**A continued visit gets back the spoon and every caddy full of its own tea.** A burnt spoon or a caddy washed down the sink would otherwise end that tea for good, since the house has no other. The loss stands for the rest of that visit, and the keeper remarks on the return. Rejected: carrying the loss over, because one mistake would close the game.

**A saved state is resumed only if it fits, and added or removed content fits.** The saved state is compared field by field with what the game reads, so a changed state throws away only the saves it would misread. A new bowl joins at its place and a removed one is left out, because content is added often and each addition would otherwise cost the player their visit.

**A liquid knows which teas it is made of.** A player may take any caddy and may boil water for no tea at all, so the tea belongs to the liquid and not to the ritual. Leaves credit the strength they add to their own tea, and pouring carries the teas with the liquid while the leaves stay in their vessel. A mixture's teas are weighted by what each contributed, its strength times its volume, so plain water dilutes the strength and not the blend. Rejected: one tea chosen for the whole ritual, the first version, because the room chose it without the player, and it judged every vessel by a tea that need not be in it.

**A mixture is judged against the average of its teas' ideals, weighted by the blend.** A sip's strength is compared with the balanced strengths of its teas, each weighted by its share of the strength, and the room colours the liquor with the teas' colours by the same weights. The drinking temperature is the same for every tea, so it stays one verdict for all.

**Nothing is judged until something is drunk.** Only then is something done with the tea. Rejected: judging the water when the heater is switched off, the kettle leaves it or a brew starts, because the water need not end up in any tea, and nothing in the room read those judgements.

**Each caddy holds its own tea, given by the room's content.** A player may take any caddy, so the room says which tea and how many grams each caddy starts with, the room opens with every caddy full, and a return refills each with its own tea. The rules find a caddy through the room's definition and never by the id `caddy`. The quiet room keeps one caddy of sencha.

**The ritual has no phases until an end screen exists.** The room never reached a phase before or after the ritual, nor sent the commands between them, so they only had to be kept working. They come back with an end screen that gives them a meaning.

### Shared/Content/

**Content is data in a `Catalog`.** A new tea, vessel, heater, figurine or room is a definition, not code. Rejected: a class per tea, because every new tea would need new code and a new review of the rules.

### Apps/Game/

**The architecture skills' MVVM is mapped, not copied.** The scene plays the view and the view model at once: it forwards taps as commands and draws the state it is given. The presenter from those skills is `Table/TablePresenter.ts`, a pure mapping from state to presentation cues: fill, colour, steam and the water's motion. Rejected: view models per object, because a game loop that redraws every frame has no binding problem for them to solve.

### Apps/Game/Texts/

**Every text the player reads is one key and one value in one file.** `Apps/Game/Texts/EnglishTexts.ts` lists them all, so the whole of the game's wording can be reviewed in one place, and a second language is a second file with the same keys. A text named by its whole key is typed, so a missing one fails the type-check. A phrase with several lines, such as a remark, a sip's feeling or the last words, is a list of at least one line in `englishPhrases`, under a key typed the same way, so the type-check finds a missing phrase or one with no line. Numbered lines counted only when the phrase was said let a phrase with no lines throw in the middle of a frame. A figurine's name is keyed by its id and has no fallback, so a figurine without a name does not compile. Placeholders such as `{figurine}` are filled by `textWith`.

### Apps/Game/Room/

**Taps become decisions in classes that do not know the renderer.** `RoomGestures` tells a tap from a stroke, a pinch or the finger that aims a pour. `RoomPlay` decides what a tap on what it hit means, and `RoomNavigator` walks. The scene only forwards pointer events, raycasts and draws. Every tap rule is then testable in Node. `RoomPlay` holds one mode: free, aiming, looking closely, sipping or ended. Every input, a tap, a key, a hold, a sip or the tilt, asks the mode first, and what the mode does not take is refused with a log line. The Sip button is shown from the same answer as the E key. The keys once called `RoomPlay` directly, so a key chose the other hand in the middle of an aim, and the next tap put down the wrong item. Rejected: logic inside input handlers, because it could only be checked in a browser.

**The room's remarks and the world's secrets are two things.** `RoomRemarks.ts` holds what the room says about what the player does during one visit: a remark changes nothing in the world and is forgotten with the visit, so it lives in the presentation as one table of facts and the remarks they earn. A secret from the world bible, such as the offerings that darken a figurine or the chains that leave a seed or a stone, remembers across visits and weeks, so it belongs in the simulation: its condition reads the world's state, its trace is an event, and what it remembers is kept in `SessionState`, saved with the visit and lived through during an absence. That engine is built together with the first such secret, because its shape cannot be known before one exists.

**A pour is aimed by a tap on the lid or the opening of a vessel, and a tap on its body takes it.** With a vessel chosen, the same tap once both aimed a pour and took a vessel, depending on whether the chosen one held anything, and the player could not see why. Now the place of the tap decides: the lid or the mouth aims a pour from the chosen vessel, empty or not, and opens the lids the pour needs, and the body takes the vessel into the other hand. An invisible touch area over each vessel's opening tells the mouth from the body. Rejected: aiming from any tap on a vessel, because taking a second bowl then needed letting go of the first.

**First person has four control schemes, and the mouse is caught like in a shooter.** Two sticks, the mouse and the keyboard, the mouse and a walk stick, or the keyboard and a look stick, so a device with only one of a mouse and a keyboard gets a stick for what it lacks, on the side the stick choice gives. The settings choose the scheme, because a page cannot tell whether a keyboard is attached. A caught mouse turns the look, and a click acts under a ring in the middle of the screen, so the look and the click never fight over the cursor. A mouse step over 150 pixels is dropped, because Chromium sends one huge step as it catches the mouse. Rejected: turning the look by dragging, because every click would then also turn the view.

**First person never leaves the keeper's eyes.** Furniture within 70 cm of the keeper is within reach, and taps act on it from where the keeper stands, so the player keeps the angle they walked up with. Rejected: a fixed close-up at each piece of furniture, because it took the view away from the player. The keeper sits only at the tea table, and only on walking there by a tap or on acting at it, so walking past the table does not drop the view. Sitting starts the look on the middle of the table. The keeper's height is a debug setting from 70 to 200 cm, 165 cm at first, raised from 140 cm because the user found 165 cm the right height, because at a fixed eye height of 1 m the counter's top and the shelf's top board were hard to see. The eyes stand at 93 % of the height, and at 55 % seated.

**Room logic that does not need Three.js does not import it.** Paths, walking, camera poses and tap decisions are plain TypeScript, so tests run in Node without a browser.

**Items are put down by choosing a hand, then tapping anywhere on a surface.** People do not think in grids, so the item lands exactly where the finger touched, and `Placement.ts` refuses only what cannot be: over the edge, on the heater, on another item, and on top of the shelf, which is not a place for things, so the shelf holds only what fits on its boards. A refused spot keeps the item in hand and the hand chosen, so the next tap can try again. Rejected: snapping to sockets, because it decides for the player where a bowl belongs.

**Pouring is aimed with two fingers.** The player chooses the hand with the vessel and taps the target. Then one finger moves the vessel over the table and the other holds a button that tilts it, and a tap without dragging ends the aiming: on a free spot of a surface it puts the vessel down there, as a tap with a chosen hand does, and anywhere else it returns the vessel to its hand. Every end of the aim lets go of the hand, a tap on a spot where the vessel does not fit too, so the next tap does not pour or put down again by mistake. That spot once ended the aim and kept the hand chosen. The pour is both a place and a gesture, so missing the bowl wets the table. The first aiming on a device shows a short note with the gesture, because the mode starts from an ordinary tap and was taken for a bug. The note is remembered in the browser's storage, which is a convenience: if the storage is gone, the note shows once more. The vessel starts to the left of its target on the screen, with its spout turned to it, so it is never hidden behind the furniture of the close-up. The finger moves the vessel by its change of position, never to where it touches, so it does not hide what it moves. The vessel may be moved past the edge of the furniture, because the player wants to move it freely. The water it spills there lands on the furniture's nearest edge, since the room has no puddles on the floor. The held tilt stops just below the flow the target's opening takes without splashing, so a narrow bowl fills over several seconds of holding and the wide caddy fills at full tilt. A splash on every normal pour read as a leaking bowl, and a caddy that filled as slowly as a bowl made the player wait for nothing. The table gets wet when the stream misses the opening or the bowl overflows. `AimedPour.ts` holds this state apart from `RoomPlay`, and knows no Three.js. Rejected: holding a finger on the target, the first version, because the pour could not miss and so had nothing to learn.

**The spoon and the cloth are carried in the hands like any item.** Taking one fills a hand, and the player sees it in a corner of the close-up, so the hands tell the truth about what is held. With the spoon's hand chosen, a tap on the open caddy scoops and a tap on a vessel tips. With the cloth's hand chosen, a stroke on a surface wipes it as the finger moves, and the cloth follows the finger on a render layer that taps pass through, so it never catches the stroke's own taps. A tap puts the cloth down like any item, and in the puddle it soaks the puddle up while it lies there. The room knows where the puddle is, so it tells the simulation that the cloth landed in it, as it reports the share of a stream that lands in a bowl, and the simulation moves the water from the puddle into the cloth step by step. The simulation checks that the tool is in a hand, and that wiping happens where the keeper stands, on the puddle there. Each place keeps its own puddle, where the missed stream fell under the spout, or around a vessel that overflowed, because one wet table for the whole room drew a spill at the counter on the tea table. Rejected: the first version, where the tools stayed on the table and a pale circle marked the one in use, because a tool held by nothing hid what the hands were doing.

**In a close-up, what the keeper holds is drawn in the bottom corners of the view, and the items are the hands.** The player sees what they carry, so no label names it. A tap on an item chooses its hand, and an invisible area around it makes the tap forgiving. The held items are drawn in a second pass over the room, after its depth is cleared, so furniture near the camera never cuts through them. The scene therefore clears to a colour instead of drawing a background, since a background clears the screen on every pass. Rejected: buttons with the item's name, because the words stood in for what the room can show.

**Tasting is a Sip button, answered by a feeling.** In a close-up the keeper is hidden, so there is no face to lift the bowl to. The keeper answers each sip with one line in their own words, because a card of temperature, strength and bitterness read like a debug report. The taste judgement tells plain water apart as a strength of `none`, so a sip of water gets its own line. Each visit gets one voice, chosen at random when the page opens, so the same feeling gets the same words for the whole visit, and a player may hear another voice after a reload. The simulation never sees the voice. A sip among leaves is a feeling of its own, so it is never just right, and Sommelier is earned only by a just-right sip with no leaves in the vessel. The user decided it: a sommelier would not drink from a bowl with leaves, and a clean bowl is better. `sipFeeling` in `Table/TableTexts.ts` decides the feeling for the line and for the achievements alike. One sip may earn several achievements, so tea brewed in a bowl earns Enlightened whatever else its sip earns.

**A warm glow marks the chosen item.** Raising the chosen item a little was not enough to tell "held" from "held and ready to use", and a tap then did something the player did not expect. A soft glow pulses behind the chosen item in its corner. An empty spoon has nothing to tip, so a tap on a vessel takes it, as an empty vessel does not aim a pour.

**An item taken by a tap is chosen at once.** Taking something is nearly always followed by using it or putting it back, so the next tap already acts with it. A chosen vessel aims a pour only when it holds something, because otherwise a tap on the next bowl would aim a pour from an empty bowl instead of taking it.

**The tap and the heater's switch are controls, and a control works whatever the hands hold.** When the sink was part of the tap's target, a tap on the tap with a hand chosen put that item in the sink and turned the water on, so the player could not turn the water off while holding anything. Now the tap only turns the water on or off, and the heater's switch only switches, even with both hands full, and a tap reaches them through the chosen hand's item. An item goes into the sink only by a tap on the sink with its hand chosen, as it goes onto any other place, and the tap stays as it was. The tap is thin, so it answers in an invisible box as wide as a fingertip, and the sink seen under that box wins the tap, as a vessel behind it does. The item in the sink is its own target, and so is its lid. Rejected: putting the item in and turning the water on with one tap, because a tap on the tap then meant two things, depending on the hands.

**A kettle with a closed lid goes into the sink, and the water runs over the lid.** The player opens the lid in the sink, as at a real sink, and the water goes in from that moment. Refusing the closed kettle made the tap look broken, and opening the lid by itself took the decision from the player. Rejected: holding the water back until the lid opens, because a tap that is open and dry is not what a sink does.

**Nerd mode shows numbers, and it is off at first.** The game is about reading water by its steam and surface, so a new player sees no numbers. A player who wants them turns on nerd mode in the settings and gets a thermostat on the heater and a thermometer on the kettle, as real kitchen things with nixie tubes, whose wire numerals glow orange, never as a label on the screen. Seven amber segments were rejected, because they read as a cheap clock and not as a thing from the house. The simulation keeps the thermostat whether or not the room shows it: switching nerd mode off hides the panel, a working thermostat keeps working, and the switch still stops it. The thermostat measures the water in the vessel on the plate, so with no water it leaves the plate cold. In nerd mode the switch heats the water up to the target on the display and holds it there, working without a break until it is switched off, because the display says what the heater does. Only the thermostat's button switches the plate off at the target and back on 2 °C below it. While the thermostat works, the heater's switch switches the heater and the thermostat off, whatever moment of its cycle it is in, and never takes the heater over by hand, as the user decided. Without nerd mode the display is hidden, so the switch boils until it is switched off, as it always did, and a kettle can still boil dry. The panel is large for its controls, because a close-up of the counter shows it only a few centimetres wide on a phone.

**The heater's switch is its own target on the counter's front.** With the kettle on the plate, a tap on the plate lands on the kettle and lifts it. A separate switch keeps "take the kettle" and "switch the heater" apart, and gives the switch a touch target of its own.

**The room opens with nothing to begin: every caddy is full of its tea, and every action is possible at once.** The player chooses a tea by taking a caddy, so the room sends no command to choose one.

**A new game arranges the room at random, and the arrangement is saved with the visit.** The room should feel lived in and a little new with each game, without new rooms to build. The window, which of the kitchen and the shelf stands beside it, the tea table's place, the tools, the cushions and the cloths are chosen apart, so they combine freely, and none of the choices is the room's usual one. `Shared/Content/Rooms.ts` places the counter, the shelf and the tea table for each arrangement, each with a position and the side it faces. Every spot on a piece is kept in the piece's own frame, so a piece that moves or turns takes its items and its sink with it. `quietRoomArrangedAs` builds the simulation's room from these placements for the catalog of that game, and `roomLayoutFor` in `Room/RoomLayout.ts` builds the drawn room from the same placements, with the arrangement's cushions and cloth patterns, so the spots and the furniture cannot drift apart. A continued visit must open the same room, because the saved state names the cloths and the spots in it, so the visit keeps its arrangement. A visit saved before arrangements existed continues in the room it was played in, and one saved before the shelf and the tea table could move keeps its window, with the kitchen beside it and the tea table by it. `Tests/Game/Room/RoomArrangements.integration.test.ts` checks every arrangement: each item starts where the room lets it be put down, the sink stands where the tap fills, every side of every piece of furniture can be walked to, and the cushions lie on the floor clear of the furniture. Rejected: one catalog room per combination, because rooms of copied data drift apart. Rejected: one hand-written `RoomLayout` per place of the kitchen, the first version, because each new place of a piece meant copying every position of the room.

**The tea table is used from the nearer of its long sides.** Walking round the table to the front, when the keeper stood by the window, looked like a detour. The navigator plans a way to each side a piece of furniture has and takes the shortest. The close-up comes from the side stood at, so the player sees the table as the keeper does. It is derived from where the walker stands, so a saved visit needs no new field. On a portrait phone the camera stands about six metres away to fit the table's width, so from the window side it is behind the back wall, and the wall and the sill fill the bottom of the screen. The view is accepted as it is, and hiding the back wall in that close-up was set aside.

**Pinching zooms the camera, the room's zoom is kept, and each close-up starts unzoomed.** The zoom only scales the camera's distance to what it looks at, so the view keeps its angle and its subject. The room's zoom is the player's choice, so it stays while the keeper walks and comes back after a close-up, and the camera flies into a close-up from wherever the player left it. A close-up starts at its usual distance because it is framed to show the whole piece of furniture. `Camera/CameraZoom.ts` keeps the two zooms apart. Rejected: resetting the zoom on every change of view, the first version, because the camera jumped out and back in on each walk. Safari's own page zoom is turned off so the pinch reaches the game. Rejected: pinching while a pour is aimed, because the first finger already moves the vessel.

**A held item is looked at up close after a hold of one second, and the look changes nothing.** The items are modelled with care, their glazes, paintings and glass, and in a corner of the view they are too small to see. A tap already chooses a hand, so looking needed a gesture of its own, and a finger held still for a second is not made by accident while choosing. Longer holds felt too long to wait. The hold is timed by the frames' real duration, not by the room's capped step, so it lasts as long on a slow phone too. The press that became a hold is not a tap when it lifts, and the tap that ends the look reaches nothing else, so the chosen hand is exactly what it was. Only the presentation knows about it: the simulation gets no command and keeps advancing. The item turns like a turntable, around its own upright and tipping towards the viewer, because a bowl or a thermos is looked at that way in the hand. The room and the other held items are dimmed behind it, and a light that follows the camera lights it from the viewer's side, so the item stands out and its gloss moves as it turns. The item is drawn in a pass of its own, and its forgiving touch area is off there, so a tap just beside it counts as outside. Rejected: a double tap, because the first tap would already choose the hand. Rejected: moving the camera to the item, because the camera's framing belongs to the close-up.

**A middle hand grows and takes its item in one command.** The simulation never holds an empty middle hand, so a take that fails, such as the spoon crumbling, grows nothing. The room decides when the player has earned it, after ten taps in a row on one item, and that it grows only once, through the Shiva achievement, so a reset of the achievements lets it grow again. Rejected: a command that only grows the hand, because the hand could then stay empty and forgotten.

**Achievements are hidden until the player turns them on.** The user decided that the player earns them without knowing: at first no medal hangs on the wall, no notice announces one, and the start-over note says nothing of them. The first row of the settings, Show achievements, turns them on and off. It is off at first, and settings saved before it read as off. Turning it on shows the medal at once, and its sheet lists everything earned so far without replaying the notices. While they are hidden they are still earned, kept and logged, so the middle hand still grows only once.

**Gourmet is earned when one vessel holds three different teas.** A liquid carries its teas, so blending them is something to find. A tea counts when it gives at least a tenth of the mixture's strength, so a drop of a third tea does not earn it. While the room's caddies hold fewer than three different teas it cannot be earned, so it is dimmed, as it always is in the quiet room with its one caddy.

**Achievements are kept apart from the visit, for good.** They are a record of the player, not of the room, so a death or Start over that clears the visit keeps them, and only Reset on their sheet clears them. Their titles are riddles and their descriptions show only once earned, so the list is something to puzzle over and not a checklist. Achievements are decided in the room from events, remarks and state, and the simulation knows nothing of them. While achievements are shown, a new one is announced by its title alone, and the sheet says what earned it. An achievement out of reach here or now is dimmed and says nothing more, because a reason would give its riddle away. `achievementsOutOfReach` in `Room/Achievements.ts` decides it from the state and the room. The Delphic Oracle is earned by a drawn frame, not by a place: `Views/ProphecySighting.ts` checks after each frame that the prophecy faces the camera, that its four corners are on the screen, and that nothing drawn in the room or the keeper stands between the camera and any corner. The painting is cropped to its ink in `Views/ProphecyInscription.ts`, and the plane on the wall takes the cropped size, so the corners are those of the words. The blank margin of the first painting kept the achievement from a player who saw every word, because its lower corners were just off the screen. The prophecy faces outside, so today only the tea table's close-up from the window side shows it. Rejected: unlocking it when that close-up opens, because a room with another layout or a zoomed camera could open it with the prophecy cut off or hidden. The garden is left out of the check, because its plants are low and it has thousands of them.

**The visit is saved every two seconds and when the page is hidden.** Mobile Safari may drop a page in the background without any event, so a save only on leaving would lose visits. A save is about 4 KB of JSON. The light, the voice and the once-a-visit jokes start anew, because a continued visit is still a new visit. The keeper's death forgets the save, so the joke of YOU DIED keeps its weight.

**Settings hang on the wall as a gear, and soft shadows in corners are off until the player turns them on.** The room has no menu bar, so the gear hangs under the medal, centred with it between the counter and the shelf. Beside the shelf it looked squeezed, and further along the wall a portrait phone cut it off. The soft shadows are screen-space ambient occlusion from three.js, `GTAOPass`, drawn only over the room's first pass, so the items held in a close-up stay clean. It costs a pass over the whole screen each frame, and a weak phone may drop frames, so the player chooses it with a warning. The settings are a convenience kept in the browser: without storage they last one visit. The face is a setting that a new game chooses at random, so a player meets a new keeper with each new game and can still change it. Hair is left out of that choice, because it is a joke for the player to find and turn on. Rejected: ambient occlusion for everyone, because the game's first target is a phone.

**The light follows the ritual's time of day, and holds still.** The room opens at a time of day chosen at random from those the room offers, through `chooseAtmosphere`, and `Sky/DaylightCycle.ts` turns that time into the sun's position, its warmth and the lights' strength, so the light is testable in Node, and `Views/RoomLights.ts` applies it. Morning, dusk and night stay in the order of the day, ready for rooms that offer them. No other rule depends on the time of day yet. The sun rises in the east behind the window wall, stands over that wall at noon, and turns in the afternoon until it faces the open front on the left, so the setting sun shines into the room and things cast shadows. A sun that set in the west behind the left wall was rejected, because no sunlight reached the room and nothing cast a shadow. Dawn starts at 0.8 hours for the same reason: earlier, the sun is still below the window wall. The plants are lit with a simpler material than the room and take no shadows, because the garden covers much of the screen in the room view and each of its pixels cost the full lighting of the room. The lawn keeps its shadows, so the house still casts one on the grass. The picture did not change in a way the user could see. With Object detail Reduced, flowers more than 3 m beyond the walls are drawn with simpler shapes, 17 to 34 faces each instead of 29 to 58, because the room ends there and the camera is never nearer than that. ### Tests/

**Tests run on Node's built-in runner, with TypeScript run directly by Node.** The core needs no packages at all, and Node 22.18 strips types on its own. The runner needs no package of its own: the tests use TypeScript for the type-check, the type packages, and Three.js where they build the room's models. Rejected: Vitest, because it adds a toolchain for what `node --test` already does. Vite builds the pages and does not run the tests.

**UI tests run on iPhone WebKit and Android Chromium and read the logs.** WebKit is the engine of iOS Safari, the game's main target. The tests read the `[room]` and `[ritual]` lines from the browser console instead of calling into the game, so the product carries no test hooks. `@playwright/test` is pinned to the version whose Chromium is preinstalled in the agent environment, so the same tests run there and in CI.

**The game's tests are type-checked with the game, and `Apps/tsconfig.json` sets its own empty `exclude`.** `Tests/Game` builds Three.js views, which need the browser's types, so the root `tsconfig.json` leaves it out and `Apps/tsconfig.json` takes it in. A config that extends another inherits its `exclude`, so without its own the game's tests were type-checked by neither config, while Node still ran them.

### Scripts/ and .github/

**The room is built by Vite.** `Scripts/build.sh` builds it to the root of the site with no config file: the command line says everything. `import.meta.env.DEV` tells the game whether it is a development build.

**The game is also published as a Claude artifact, from a build that logs nothing.** `Scripts/build-artifact.sh` builds the room with `Scripts/silent-build.vite.config.mjs`, which takes every log call out of the code together with its text, so neither the console nor the script spells out the rules. The rules' log lines describe them in plain words, so a logger that only writes nothing still left them in the file. The room and the ritual also get logs that write nothing, in case a call is missed. An artifact takes one page with its script inside, so the build puts the page, its styles and its script into one file. The page is called TeaCeremony, and the browser storage keys carry no name of the game. CI does not build the artifact, because the user decided it does not need to: the agent that publishes it runs `Scripts/build-artifact.sh` itself.

**GitHub Actions tests every push and deploys to Pages from the default branch.** The workflow reads the default branch from the event instead of naming `main`, so it keeps working if the default branch is renamed. Action versions are the Node 24 majors (`checkout@v5`, `setup-node@v5`, `upload-pages-artifact@v5`, `deploy-pages@v5`, `cache@v6`, `upload-artifact@v7`), because GitHub is removing the Node 20 runtime from its runners in September 2026. The npm packages are kept between runs, keyed by the lockfile, and each UI test's browser, keyed by the revision Playwright installs, so a run downloads them again only when they change. A restored browser still gets its system libraries installed, because the runner starts clean. Rejected: a container image with those libraries, because it was measured on CI and was not faster: the WebKit job went from 63 s to 68 s, and the Chromium job from 84 s to 90 s. A new push to a branch cancels the tests and the build still going for the same branch, because only the newest commit is worth testing, and the older jobs waste minutes. A deployment already under way is never cancelled: it has its own concurrency group, and the next one waits for it, so a site that is half published always finishes. The tests, the build and the UI tests of each browser run as separate jobs at the same time, and Playwright runs the tests of one file in parallel, because one job doing all of it in turn took most of two minutes on every push. Deploying waits for all of them.

**Every script lives in `Scripts/`, and each configuration file lives beside what it configures.** A newcomer finds every command in one folder. The root `tsconfig.json` checks `Shared` and the simulation's tests without the browser's types and is the one editors find, `Apps/tsconfig.json` adds the browser's types for the apps and the game's tests, which build the room's models, and `Tests/Browser/playwright.config.ts` sits with the browser tests it runs. Rejected: scripts beside their configuration files, because the commands would then be spread over several folders.

## Corrections that stuck

### Project

**Screenshots and scratch output never go into the repository.** Twice, pictures from a browser check landed in the repository's root, because the check ran from there. Checks run from a scratch folder outside the repository, and files are staged by name.

### Apps/Game/Room/

**Nothing is drawn through anything else.** Several times a thing was placed at a fixed offset and passed through its neighbours: open lids lay in the sink's sides, on the heater and in a bowl beside them, the thermos stood through the sink's floor, and an overflow started off the vessel's wall. Every spot a thing is drawn at comes from `Placement.ts` or is checked against the furniture, the heater, the sink and the other items there, and a spot that is taken is refused or moved, never overlapped. An item's footprint in `CarriedShapes.ts` is every part that reaches past its body: the kettle's spout is a second circle, which may hang over an edge, the sink or the heater, but never over another item. A change that draws something at a new spot is checked in a close-up next to its neighbours before it is done.
